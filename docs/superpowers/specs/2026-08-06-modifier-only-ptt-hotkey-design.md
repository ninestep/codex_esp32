# 纯修饰键 PTT 快捷键设计

## 背景与结论

Codex Remote 当前把豆包语音快捷键配置为独立 `Fn`，并通过 `CGEvent` 合成按下和释放事件。现场验证表明，豆包输入法 0.9.5 能识别物理 Fn，却不识别合成 Fn。改变 Fn 的 `CGEventType` 不能解决该限制。

豆包只允许使用 Fn、Command、Option、Control 的单键或组合键。采用 `Command + Option`（显示为 `⌘⌥`）作为 PTT 快捷键。Codex Remote 在设备按下时合成两个修饰键的按下状态，在设备松开时按相反顺序释放。

## 范围

本次改动包含：

- 支持由两个或三个 Command、Option、Control 组成的纯修饰键组合。
- 将纯修饰键组合强制归一化为按住型。
- 以确定顺序发送按下事件，以相反顺序发送释放事件。
- 在部分发送失败时释放已经按下的修饰键。
- 移除设置页的 Fn 快捷入口和 Fn 可用提示。
- 更新相关单元测试和设备启用文档。

本次改动不修改 BLE 协议、ESP32 固件、音频编码、BlackHole 路由或会话模型，也不自动修改豆包输入法配置。

## 输入规则

解析器继续支持现有的“修饰键 + 普通按键”格式，并新增纯修饰键组合：

- 允许的修饰键：`⌘`、`⌥`、`⌃`，以及对应英文名称。
- 纯修饰键组合至少包含两个不同修饰键。
- 纯修饰键组合不允许 Shift。Shift 在日常输入中频繁使用，也不在豆包提示的可选单键列表内。
- 独立 Fn 和包含 Fn 的组合均拒绝，并返回明确错误。
- 纯修饰键组合的显示顺序固定为 `⌘⌥⌃`，不受输入顺序影响。
- 纯修饰键组合强制使用按住型。

首个现场配置使用 `⌘⌥`。

## 事件模型

每个修饰键包含虚拟键码和对应 flag。以 `⌘⌥` 为例：

1. Command down：发送 `flagsChanged`，flags 为 Command。
2. Option down：发送 `flagsChanged`，flags 为 Command + Option。
3. Option up：发送 `flagsChanged`，flags 为 Command。
4. Command up：发送 `flagsChanged`，flags 为空。

释放顺序与按下顺序相反，避免短暂产生错误的修饰键状态。普通“修饰键 + 主键”继续使用现有 key-down/key-up 路径。

## 失败恢复

发送任一按下事件失败时，发射器按相反顺序释放本次已经按下的修饰键，然后向上返回失败。发送释放事件失败时，恢复逻辑尝试释放组合内全部修饰键。恢复失败不伪装成功；上层仍收到原始发送失败。

PTT 开始失败时，`BlackHoleAudioInputBridge` 继续恢复默认输入设备并停止音频引擎。PTT 结束或连接中断时，现有 `abort()` 路径释放活动快捷键并恢复系统输入设备。

## 界面与迁移

设置页删除“使用 Fn”按钮。提示文案改为要求用户输入豆包实际配置的纯修饰键组合，例如 `⌘⌥`。保存旧的 Fn 配置时显示格式错误，不自动映射为 `⌘⌥`，避免未经用户同意改变外部快捷键语义。

已安装应用中的旧 Fn 设置仍可读取，但语音就绪状态应提示用户重新配置。用户在豆包和 Codex Remote 两端设置相同组合后保存，新配置立即替换运行时音频桥。

## 验证

自动验证覆盖：

- `⌘⌥` 和三个修饰键组合的解析、归一化及按住型约束。
- 单个修饰键、Shift、Fn、重复修饰键和混合非法输入的拒绝。
- `⌘⌥` 的按下顺序、累计 flags、反向释放顺序。
- 部分按下失败和释放失败后的恢复。
- 连续两次 PTT 产生两组完整的按下和释放事件。
- 现有普通组合键测试保持通过。

现场验证依次执行：物理 `⌘⌥`、设置页快捷键测试、ESP32 第一次 PTT、ESP32 第二次 PTT。四项均触发豆包语音并正确结束后，才判定修复完成。
