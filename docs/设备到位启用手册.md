# Codex Remote 设备到位启用手册

## 当前结论

Mac 端普通安装主路径已收敛为向导操作：打开 Codex Remote，运行自动配置，按提示完成 `/hooks` 信任、BlackHole 独立确认和系统权限，再连接设备执行综合测试。用户不需要手工编辑 hooks 或 shell 配置。

仓库构建不会自动烧录设备，也不会自动安装 BlackHole、修改真实用户配置、申请系统权限或发送豆包快捷键。每项外部变更都需要用户在现场确认。

## 1. 准备产物

### ESP32 固件

已有构建产物：

```text
firmware/build/bootloader/bootloader.bin
firmware/build/partition_table/partition-table.bin
firmware/build/codex_remote.bin
```

设备首次到位后，通过 USB 确认串口，再执行：

```bash
cd firmware
idf.py -p <PORT> flash monitor
```

这是会写入设备的现场操作，执行前必须再次核对 `<PORT>` 确实属于目标 ESP32-S3。先使用现有分区和 NVS，只观察启动、屏幕、触控、GPIO18、麦克风和 BLE 广播。

### Mac App

构建本机验证包：

```bash
cd macos
zsh Scripts/package-app.zsh release
```

产物为 `macos/dist/Codex Remote.app`。当前是 ad-hoc 签名，适合本机验证；不是面向第三方分发的 Developer ID 签名和公证版本。

## 2. Mac 一键配置主流程

1. 打开 `Codex Remote.app`。首次检查未通过时会自动显示“Codex Remote 安装配置”窗口；之后也可从菜单栏进入“设置… → 安装与诊断”。
2. 在“基础环境”确认 Ghostty 和 Codex CLI 已就绪。如果 App 不在固定位置，进入下一步让向导复制到 `/Applications/Codex Remote.app`。
3. 进入“自动配置”，点击“开始自动配置”。确认框会明确列出可能修改的目标：
   - `/Applications/Codex Remote.app`
   - `~/.zshrc`
   - `~/.codex-remote/bin/codex`
   - `~/.codex/hooks.json`
4. 核对目标后确认。若向导完成 App 安装，它会暂停并要求关闭当前临时实例；请手工从 `/Applications/Codex Remote.app` 重新打开，避免权限身份随启动路径变化。
5. 重新打开后继续自动配置。向导会安装透明 `codex` shim、前置受控 PATH，并把本工具 hooks 合并到现有 `~/.codex/hooks.json`，不会覆盖无关 hooks。
6. 流程在“Hooks 信任”处暂停。打开 Ghostty，通过新的 `codex` 命令启动会话，在 Codex 中运行 `/hooks`，审查并信任新增 command hooks，然后启动一次测试会话。返回向导点击继续复查。
7. 如果缺少 BlackHole 2ch，向导会单独显示安装说明和 `brew install --cask blackhole-2ch`。只有再次确认后才会安装；“开始自动配置”的首次确认不包含 BlackHole 安装。
8. 分别按向导按钮申请蓝牙、麦克风和辅助功能权限。在系统设置完成授权后，退出并从 `/Applications` 重新打开 App，再点击复查。
9. 先在豆包输入法中把语音快捷键设为 `⌘⌥`，再进入 Codex Remote“功能测试”，点击快捷键录制框，实际按住 `Command + Option`，全部松开后保存。纯修饰键组合固定使用“按住”模式。点击测试后有三秒倒计时；请先让豆包输入目标处于可观察状态，再确认一次完整按下和释放生效。
10. 本地 IPC 和 Mac 必需项通过后，连接 ESP32，执行综合测试。真机等待不会被误判成 Mac 配置失败。

## 3. 真机综合验收

按以下顺序验收，任何一步失败都先停在该层排查：

1. 设备能启动并显示首页，Mac 菜单栏显示 BLE 已连接。
2. 在 Ghostty 中通过透明 shim 新开 1 个 Codex 会话；设备首页出现对应卡片，状态颜色随会话变化。
3. 再开多个会话，验证最多显示 8 个；首屏 2×2 共 4 个，纵向滑动可查看其余会话。
4. 点击某会话卡片进入详情，Ghostty 自动切换到对应标签页/终端。
5. 在详情页纵向滑动，目标 Ghostty 终端同步滚动，不影响其他会话。
6. 触摸 Enter/Esc 按钮；再验证 GPIO18 单击 Enter、双击 Esc。
7. 未进入任何会话时长按实体键，PTT 必须不可用且不得触发豆包。
8. 进入会话后长按 GPIO18 说话，确认 `⌘⌥` 被按下并触发豆包语音识别；松开后确认快捷键释放、识别结束且系统默认输入恢复。首次和第二次 PTT 都必须成功。
9. PTT 中主动断开 BLE，确认 Mac 中止 PTT、释放快捷键并恢复原输入设备。
10. 验证 60 秒降亮、120 秒内置状态屏保、300 秒息屏和实体键唤醒；PTT 期间保持常亮，琥珀/红色状态点亮 8 秒。

## 4. 豆包和音频说明

PTT 开始时，Mac App 保存当前默认输入设备，将 BlackHole 2ch 设为默认输入，把设备传来的 16 kHz 单声道音频播放到 BlackHole，并按设置触发豆包语音快捷键。PTT 结束、BLE 断开、音频失败或 App 正常退出时，App 都应释放快捷键并恢复原输入设备。

豆包当前能识别物理 Fn，但不能识别 Codex Remote 通过 macOS 事件接口合成的 Fn，因此不要把 Fn 配置为 PTT 快捷键。豆包和 Codex Remote 两端统一使用 `⌘⌥`；Codex Remote 会按 `Command → Option` 的顺序按下，并按相反顺序释放。推荐先在“功能测试”页只测快捷键，再连接设备测试音频，以便区分快捷键、系统权限、BlackHole 路由和 BLE 音频问题。

## 5. 故障排查

### 向导没有自动出现

从菜单栏选择“设置…”，打开“安装与诊断”；也可选择“完成安装配置…”。长期诊断页与首次向导读取同一套检查结果。

### App 已复制但流程没有继续

关闭临时位置启动的实例，确认实际打开的是：

```text
/Applications/Codex Remote.app
```

向导故意不从临时路径自动重启，避免蓝牙、麦克风和辅助功能授权绑定到不稳定路径。

### 新 shell 仍调用旧 Codex

打开新的 Ghostty shell，检查：

```bash
command -v codex
type -a codex
```

受控 shim 应优先于真实 Codex；shim 会继续调用真实 Codex，并原样转发参数、标准流和退出码。不要手工覆盖真实 Codex 可执行文件。

### Hooks 没有生效

在 Codex 中运行 `/hooks`，确认新增 command hooks 已审查并信任；然后通过透明 shim 新开测试会话。不要用仓库模板直接覆盖 `~/.codex/hooks.json`。

### BlackHole 或语音不可用

先确认豆包和 Codex Remote 都配置为 `⌘⌥`，再回到“安装与诊断”确认 BlackHole 2ch、麦克风权限、辅助功能权限和快捷键测试都已就绪。若物理 `⌘⌥` 能触发而设置页测试不能触发，退出并从 `/Applications/Codex Remote.app` 重新打开，再复查辅助功能授权。BlackHole 安装属于系统依赖变更，必须通过独立确认执行。

## 6. 已知未完成项

- 自定义 JPEG 图片传输、持久化和轮播尚未接入；当前只有内置状态屏保。
- BLE 使用加密和 Secure Connections，但当前是 Just Works 配对，设备侧没有数字确认 UI，因此未启用 MITM。
- ATT MTU、持续音频吞吐、丢帧、触控坐标、GPIO 抖动、功耗和电量读取仍需真实设备数据。
- 未生成 Developer ID 签名、公证、DMG、LaunchAgent 或自动更新。

## 7. 回滚边界

- hooks：使用向导的受控恢复；或恢复安装前备份的 `~/.codex/hooks.json`，再在 Codex `/hooks` 中确认新增项消失。
- shim/PATH：使用向导恢复受控 PATH 块和自有 shim；之后 `command -v codex` 应重新指向真实 Codex。
- App：退出并移除 `/Applications/Codex Remote.app`，在系统设置中撤销其蓝牙、麦克风和辅助功能权限。
- BlackHole：只有在用户单独确认安装后，才按当时 Homebrew/cask 状态提供对应卸载步骤；不要把卸载和普通 App 回滚绑定执行。
